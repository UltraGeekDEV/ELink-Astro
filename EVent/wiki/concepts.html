Core concepts

The vocabulary of EVent and NOTES, explained once.

These are the ideas you need to read the rest of the wiki and the code. Each one links to the page that covers it in depth.

Node

An EVentNode is a router living in one process. It has a NodeID string, which appears only in debug output and is never sent over the wire (I-38), plus a set of transports and a set of connected clients. A process can host several nodes. The Examples run three.

Client

Anything the node exchanges packages with implements IEVentClient: ID, Send(Package), ReadPackage() and Shutdown(). There are two implementations:

  • QueuedClient: a link to another node through a transport.
  • LocalCallbackClient: your code in the same process. The node's read loop reads what you fire, and the node's Send delivers to your callbacks.

The router treats both the same way. That symmetry is the core of the design.

EventID

A plain string that names an event or a function. There is one flat namespace shared by user events, user functions, EVent admin messages and NOTES system functions. The reserved names are listed in Event ID constants. Don't reuse them, and don't use the same ID for both a raw event and a function (the raw subscriber answers calls with nothing). IDs are flat strings, but dots have a meaning to namespace nodes and prefix routes: Minecraft.Player.Health is Health inside the Minecraft.Player namespace. IDs starting with $ belong to namespace nodes.

Interest

A client is interested in an EventID once it has sent the node an EventAdded admin message for it. The local client sends one the first time you HookEvent or RegisterFunction. The node records this in two maps:

EVentNode.cs:23-25
Dictionary<string, HashSet<IEVentClient>> events;   // EventID -> clients that want it
Dictionary<IEVentClient, HashSet<string>> clients;  // client  -> EventIDs it wants

and forwards the announcement to all its other clients, so interest spreads across the network. For a remote link, “interested” means “something on the far side of this link wants the event”. Data is only ever sent toward interest. See Links & interest routing.

Package

The unit on the wire: an EventID, a PackageType and a byte payload, framed with a length prefix. See Wire format.

Interconnect

A link between two nodes, made by a transport's EstablishInterconnect (outbound) or accept loop (inbound). Both ends then run the handshake above. TypeSafeEVentNode.TryEstablishConnection is the safe, NOTES-aware way to create one. See the link handshake and merging networks.

IBinaryConvertible

The abstract base class (despite the I) for everything that goes on the wire. It has a Name (a type name that becomes part of NOTES signatures), a Descriptor (a NOTESDescriptor listing the fields) and ToBytes / FromBytes(ref Span<byte>). See Defining NOTES types.

NOTES descriptor and signature

Every composite IBinaryConvertible registers its fields in a static NOTESDescriptor. Describing that type graph gives a signature: one =Root entry and one definition per record type, such as ["=Kennel", "Cat{Age:UInt64,ID:UInt64,Name:string,Owner:string}", "Kennel{Cats:Cat[],Street:string}"] (grammar). The signature, the layout it defines and the JSON that describes it are called NON. A NOTESEventDescriptor pairs an EventID with a signature. A descriptor can be potential (proposed) or established (agreed network-wide). See What is NOTES?.

Execution gate

A small open/closed latch with an in-flight counter (ExecutionGate). Every HookEvent/FireEvent on a TypeSafeEVentNode passes through it, so a network merge can close the gate on every node, wait for in-flight operations to drain, change descriptors, and then reopen it. It is a crude network-wide mutex.

Firewall and namespace nodes

A policy layer is two full typed nodes joined by a link that decides what one sees of the other. A firewall node passes only the events and calls its policy allows, per direction, and hides the rest (not even interest crosses). A namespace node renames: the inner network's X is ns.X outside, the outside is invisible inside except for the names the namespace imports, and the outer network routes the whole namespace as one prefix route. Both are ordinary nodes to the networks on either side, so they compose.

NON and scripts

NON dynamic objects (NONSchema, NONObject) read, build and send values of any agreed type without a C# class, and can define new types at run time. The scripting node builds on them: it generates C# classes from the agreed types of the endpoints you choose, and runs your code between them.
