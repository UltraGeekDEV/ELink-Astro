Links & interest routing

How nodes introduce themselves, share interest, and forward events toward the nodes that want them.

This page explains how EVentNode builds its routing tables, how two nodes introduce themselves when a link comes up, and how events are forwarded. Everything here is in EVentNode.cs.

Routing state

FieldTypeMeaning
eventsDictionary<string, HashSet<IEVentClient>>For each EventID, the clients (links or the local layer) that want it.
clientsDictionary<IEVentClient, HashSet<string>>The reverse index, used to clean up when a client disconnects.
functionCallbacksDictionary<EVentFunctionHandle, Action<EVentFunction>>What to do when a pending dRPC call completes (see dRPC).
awaitingResponseDictionary<EVentFunctionHandle, (HashSet<IEVentClient>, EVentFunction)>The clients that still owe an answer for each pending call, and the results collected so far.
functionEventsDictionary<string, HashSet<EVentFunctionHandle>>Pending calls per EventID.

All of these are guarded by clientLock. The node doesn't store which node is behind a link, only which events flow through it.

Link handshake

A link can come from a transport's accept loop (inbound) or from EstablishInterconnect (outbound). Either way the node calls AcceptClient(client) EVentNode.cs:247–255, which registers the client with an empty interest set, sends it InterconnectRunning, and starts its read loop. Both ends do this, so the exchange is symmetric:

HandleListEvents calls HookClient for every listed ID, which announces the IDs that are new to this side of the link to the rest of the network (next section), and then raises OnConnected(list). TypeSafeEVentNode uses that hook to share NOTES descriptors with the newly joined network.

Interest propagation

When a client announces interest, the node records it and tells the partners that didn't already route the event here EVentNode.cs:450–511:

private void HookClient(IEVentClient client, string eventID)
{
    lock (clientLock)
    {
        // subscribers = events[eventID]; if it already contains client: nothing changed, stop.
        // A partner routes eventID here once some link OTHER than the partner is interested, so tell exactly
        // the partners for which that just became true: every earlier subscriber was the partner itself (or none).
        partners = clients.Keys.Where(x => x != client && earlier.All(e => e == x));
    }
    SendEventAdded(eventID, client, partners, newToThisNode);
}
// SendEventAdded: send EventAdded(eventID) to those partners; if the event is new to this node, also
//                 raise OnEventAdded(eventID) and SendData() it to "EventAdded" subscribers

An event the node already routes is therefore not announced again: a second subscriber on the same side, a repeated list, or a new link bringing events both sides already have costs no traffic beyond the link itself. Before commit e5b2492 every HookClient re-announced unconditionally, so each entry of every event list flooded the whole network again.

The receiving node does the same thing, with the link it came from as the interested client. The announcement travels outward, and every node ends up with a reverse path pointing toward the subscriber:

The local client keeps a set, NodeEvents, of EventIDs that someone else is interested in. LocalCallbackClient.FireEvent only hands a package to the node if the ID is in that set (or it's an admin package), so firing an event nobody wants costs nothing on the network. Local subscribers on the same node are always called directly.

Individual changes reach NodeEvents through EventAdded/EventRemoved messages as they happen. A layer attached to a node that already routes events (there's no requirement to attach before linking any more, since commit 2d1d400) also asks for the current list outright, the same way a real peer would: a QueryEvents it queues for itself at construction is answered, once the node starts reading from it, with a batched ListEvents it now knows how to read.

Removing interest

Removal happens in two ways:

  • Explicitly: a local layer's last callback and last function for an ID are gone (LocalCallbackClient.UnHookEvent, UnregisterFunction), or a peer sends EventRemoved. UnhookClient EVentNode.cs drops the client from events[id].
  • On disconnect: when a client's read loop ends (ReadPackage returned null or threw), RemoveClient EVentNode.cs:269–310 does the same for every ID that client wanted. It also takes the client off every pending dRPC call, so those calls can complete with partial results.

Who is told mirrors adding: a partner routes the event to this node while some client other than the partner itself wants it, so EventRemoved goes to exactly the partners for which that just stopped being true: the one link that is now the only interested client, or every link when nobody is left (then the node also drops the entry and raises OnEventRemoved). The removal travels back along the path until it reaches a node where someone else still wants the event, so no route is left pointing at nobody (C13, C35; before commit 66d8332 a node only announced a removal when no client wanted the event, which left stale routes behind). Removing a client also completes any dRPC call still waiting on it (C08).

Forwarding data

Every package that is not an admin, call or return package goes through the default branch of ProcessData EVentNode.cs:203–212:

await SendData(package, client);          // every interested client except the sender
DataReceived?.Invoke(package, x => { });  // OnDataReceived hook: fires on every node the package passes

SendData takes a snapshot of events[package.EventID] under the lock, removes the sender, and awaits client.Send for each one. For a QueuedClient that only enqueues the package. For the LocalCallbackClient it dispatches callbacks to the thread pool. SendData is public, so you can inject a package into routing yourself.

Note

OnDataReceived fires on transit nodes too, not only where there's a subscriber, which makes it handy for tracing. Its second argument, a “reply” action, is a no-op (I-29).

Prefix routes

An interest entry that ends in .* is a prefix route: a client that announces Minecraft.* is sent every event and call whose ID starts with Minecraft.. It is announced, withdrawn and propagated exactly like an event ID (the same EventAdded/EventRemoved/ListEvents packages, the same partner rules), so it costs one routing entry per node however many IDs it covers. When a node routes an ID, it takes the clients interested in that ID by name and adds those of every prefix route covering it, one per dot: Minecraft.* and Minecraft.Player.* for Minecraft.Player.Health. That is a few dictionary lookups per package, not a scan.

// On any node: route everything under Minecraft. to the link that announced Minecraft.*
EVentNode.IsPrefixRoute("Minecraft.*");                       // true
EVentNode.CoveringPrefixRoutes("Minecraft.Player.Health");    // "Minecraft.*", "Minecraft.Player.*"

Prefix routes are what namespace nodes announce, and what firewall rules can match. A local layer (LocalCallbackClient) sends a raw event when the node routes it either way; its own hooks stay exact. A node doesn't know which IDs exist behind a prefix route, so a call for an unknown ID is carried to the node that announced it and answered there with nothing.

Admin event handling

Every ServerAdminEvent except LinkFault is first passed to SendData(package), which forwards it to clients that subscribed to that admin ID, without excluding the sender. It is then handled:

CreateInterconnectOnly from the node's own local layer (a peer can't make a node dial; it's ignored from links). Calls EstablishInterconnect(package) on every transport of this node in parallel and waits for all of them. Each non-null result remembers the connection info (for LinkFault.Redial) and is passed to AcceptClient.EVentNode.cs
DisconnectInterconnectRemoveClient(sender), then sender.Shutdown().EVentNode.cs:132–137

Topology rules

  • The network must be a tree. This is by design: the core doesn't detect duplicates or suppress loops, which is left to higher layers. A cycle makes every announcement and every data package circulate forever. TypeSafeEVentNode.TryEstablishConnection refuses any link that would close one (Loop prevention), so a network joined only through it stays a tree. Raw links (CreateInterconnect, AcceptClient) are the caller's responsibility.
  • Links are symmetric. It doesn't matter which side dialled.
  • A node may have any number of links, over any mix of transports.
  • A firewall or namespace node is a link too, as far as loops go. Its merge control doesn't cross by default, so a loop that closes through two of them (or one of them and a plain link) isn't detected (I-50).
  • Delivery is at most once per path, with no acknowledgement for raw events. A link that drops takes its queued packages with it.

Faults and re-joining

Reliable, ordered delivery is the transport client's job (a TCP-like layer over lossy links such as serial). So when a link delivers something malformed, the link can't be trusted any more: the node drops that link, never the process (commit c08d67b):

  1. Every parser validates its input and returns false instead of throwing. Package.ReadPackage throws MalformedPackageException for a bad frame, and returns null only when the stream ends.
  2. A bad frame, or a package whose payload doesn't parse (an admin message, a function call or return), makes the node mark the link as faulted: nothing more from it is processed.
  3. The node sends the peer a LinkFault package carrying the reason, removes the link from routing (pending dRPC calls continue without it), and closes the link after flushing the notice. If the peer stops reading, the link is closed after EVentNode.LinkFaultFlushTimeout (2 s) anyway.
  4. Both sides raise OnLinkFault: this node with ReportedByPeer = false, the peer (on receiving LinkFault) with ReportedByPeer = true.

Exceptions thrown by the application's own handlers (OnDataReceived, OnConnected, OnEventAdded, OnEventRemoved, OnLinkFault) are caught and logged; they don't drop links. The in-process local layer is never dropped: a bad package from it is only discarded and reported.

Re-joining is policy, so it's left to the application. The side that dialed the link gets its connection info back in LinkFault.Redial (it's null on the accepting side):

node.OnLinkFault(fault =>
{
    Console.WriteLine($"link dropped: {fault}");
    if (fault.Redial != null)
        Task.Run(() => node.TryEstablishConnection(fault.Redial));   // never block inside the handler
});
Caution

A peer can send LinkFault at will, so a re-join policy should back off (and give up after a few attempts); otherwise a faulty or hostile peer can keep the dialing side reconnecting. Harness N40 shows the re-join above working through a full NOTES merge.
