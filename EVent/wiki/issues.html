Issues & open questions

Everything unclear, inconsistent, undocumented or questionable found while documenting the code, ranked by severity.

This page collects everything that looked unclear, inconsistent, undocumented, buggy, or like a design problem while the source was being read for this wiki, plus what the test harness found when run against the real code. The rest of the wiki doesn't paper over these. It links here instead.

How to read this

I-02 to I-38 come from code review. I-40 to I-45 were discovered by running the harness, I-46 and I-48 were raised by the project owner, and I-50 and I-51 concern the policy layers and the scripting node. (Fixed and removed: I-39, the NOTES corruption race, in commit e2e550c; I-07, poisoned event IDs, and I-10, the dead Finalize retry, in commit 7e35633; I-06, the endless retry after a merge, and I-14, partial descriptor sharing after a merge, in commit 6bbe9c2; I-08, the missing type check on agreed events, I-11, the per-event serializer cache, and the empty signature of leaf-typed events (found by N32), in commit c0a0c42; I-13, the bogus "null" descriptor, and I-15, the leaked merge probe, in commit 56bab8b; I-46, collections opaque to NOTES, in commit 729bbe2, which made collections and recursive types part of the NOTES type graph; I-05, I-21, I-40 and I-41, the process crashes and unvalidated parsers, in commit c08d67b. I-04, handlers on the link reader, I-17, the gate's races, and I-42, thread-pool starvation, in commit 2c9a853, which made the core async; I-02, calls that never completed when a raw subscriber shared the ID, and I-49, a latency hole in the first loop check (two merges over a slow link could both go through), in commit 8c7a5cf; I-20, a local layer attached after the node already knew about events never learning them, in commit 2d1d400; I-18, stale routes after an unhook, in commit 66d8332; I-26, TypeSafeEVentNode API gaps (unhook, unregister, Stop, and FireEvent failing only on a type mismatch), in commits 99ebca3 and 6a95233; I-31, invalid JSON from NOTESDescriptor.ToString, in commit 2e26d05; I-23, TCP servers that couldn't be stopped and fragile discovery, and I-25, direct TCP links that never dialed without SourcePort, in commit eec0a03; I-03, calls, discovery and the NOTES start-up poll that could block forever, which now all time out (EVentNode.FunctionCallTimeout or a per-call timeout and CancellationToken, ClientTCPDiscovery.Timeout, TypeSafeEVentNode.StartupTimeout), in commit a00a3a4. Open questions for the author

  1. Are typed events meant to be synchronous and acknowledged (dRPC), or is that a stepping stone toward typed fire-and-forget events? (Integration)
  2. Is the “larger random weight wins” behaviour intended? (I-24)
  3. What's the intended use of OnFunctionCall, OnDataReceived's reply action, IPostProcessor? (I-29, I-37)
  4. Where do the non-.NET implementations (for example serial device firmware) live, and is there a normative protocol spec? (I-35)
  5. Should a network-wide StopEvents be callable by any node, or is some trust model planned?
  6. What does the MaxPackageSize comment “~100Mp 16 bit mono+ 2Mb overhead” refer to? (100 megapixel images?)
  7. Which namespace root, EVent or Event, is canonical? (I-30)

All findings

I-09 · Serial links are dropped after about 1 second of silence and never re-established

highbug
Where
SerialStreamClient.cs:118–128, EVentNode.cs:70, SerialServer.cs:41–53
What the code does

SerialStreamClient.ReadPackage returns null if no byte arrives within 1000 ms. EVentNode.RunClient treats a null package as “link closed” and removes the client. SerialServer keeps the port in alreadyCheckedPorts for as long as the OS still lists it, so it never re-runs the handshake.

Why it matters

Any serial peer that is quiet for more than a second is disconnected permanently. This is probably fine for a streaming sensor and fatal for everything else.

Suggestion

Separate “no data yet” from “closed” (keep waiting, or use keep-alives), and remove the port from alreadyCheckedPorts when its client closes.

Harness
untested Serial is iced; no hardware in the harness.

I-16 · The serial receive buffer is fixed at 250 bytes

mediumbug
Where
SerialStreamClient.cs:130–141
What the code does

ReadPackage allocates new byte[250] and reads packageLen bytes into it without checking the size.

Why it matters

Any package larger than 246 bytes (a typical ListEvents or EVentFunction quickly is) throws ArgumentException. The exception escapes to RunClient and drops the link. The length also isn't checked against Package.MaxPackageSize.

Suggestion

Allocate packageLen + 4 bytes after validating the length, the same way Package.ReadPackage(Stream) does, and throw MalformedPackageException for a bad length so the drop comes with a LinkFault notice like on TCP (today the serial link just disappears).

Harness
untested Serial is iced.

I-19 · Thread-safety gaps in shared collections

mediumbug
Where
EVentNode.cs:231–246, LocalCallbackClient.cs:236, LocalCallbackClient.cs:254, TypeSafeEVentNode.cs:202, TypeSafeEVentNode.cs:266
What the code does
  • EVentNode.GetEvents enumerates events without clientLock. (Stop did the same with clients until commit 6ed9e35.)
  • LocalCallbackClient.FireEvent reads NodeEvents (a HashSet) outside callbackLock, while the admin callbacks write it.
  • TypeSafeEVentNode.HookEvent / FireEvent read establishedEvents and write SerDesCollection without typeLocks.
Why it matters

This can cause InvalidOperationException (“collection was modified”) or corrupted hash sets under concurrent load.

Suggestion

Snapshot collections under their locks, or switch to concurrent collections.

Harness
partly C16: 4 s of concurrent hook/unhook/fire churn raised no exceptions. The Stop() problem turned out worse than predicted (I-41).

I-22 · SerialServer probes every unknown serial port every second

mediumdesign
Where
SerialServer.cs:41–55
What the code does

A port is added to alreadyCheckedPorts only when the handshake succeeds. Every other port is opened at 9600 baud and sent a SerialHandshake package once a second, indefinitely.

Why it matters

This writes binary data to unrelated devices (modems, other microcontrollers, industrial equipment) over and over, and each probe blocks the scan loop for up to 1 s (the read timeout).

Suggestion

Remember failed ports until they disappear, make the port list or pattern configurable, and back off between retries.

Harness
untested Serial is iced.

I-52 · A peer can make a link allocate up to 202 MiB per frame

mediumdesign
Where
Package.cs (ReadPackage)
What the code does

Package.ReadPackage allocates the whole frame as soon as it has read the 4-byte length, up to MaxPackageSize (202 MiB), before a single payload byte arrives.

Why it matters

Any peer (or a corrupted stream that still passes the length check) can make each of its links allocate that much, and a few links exhaust memory. The raw-event budgets (QueuedClient.MaxQueuedDataBytes) don't cover it: they count frames once read. On trusted networks it is mostly a robustness issue; on microcontroller peers it matters more.

Suggestion

Read large frames in chunks (growing the buffer as bytes arrive), and allow a lower per-link maximum; the planned handshake v2 (see Roadmap) lets each side state the largest frame it accepts.

Harness
untested Split out of I-43 when back-pressure was fixed.

I-12 · BinaryConvertibleString and BinaryConvertibleCollection override Equals without GetHashCode

lowbug
Where
BinaryConvertibleString.cs:48–55, BinaryConvertibleCollection.cs:94–114
What the code does

Both types override Equals (by text, and element-wise) but not GetHashCode, so two equal values normally hash differently. (NOTESEventDescriptor had the same problem plus an asymmetric subset test; both were fixed in commit e2e550c.)

Why it matters

HashSet, Dictionary keys and Distinct() treat equal strings and collections as different, for example if BinaryConvertibleString is used directly as a set element or LINQ key.

Suggestion

Implement GetHashCode consistently with Equals (Text.GetHashCode(StringComparison.Ordinal); a combined hash over the elements).

Harness
partly The NOTESEventDescriptor part was confirmed by U04 and is fixed (U04 now passes). The remaining GetHashCode gaps aren't exercised by the harness.

I-27 · The purpose of the gate Close/Open in the constructor is unclear

lowunclear
Where
TypeSafeEVentNode.cs:28–49
What the code does

The constructor closes the gate, registers the NOTES functions, re-opens the gate, and then polls AwaitReady. AwaitReady only waits for the gate to be open. Nobody can call HookEvent or FireEvent before the constructor returns, so the Close/Open pair seems to have no effect. The real purpose of the poll is to wait until the local client's EventAdded messages have been processed by the node, which is what makes the node answer function calls.

Why it matters

A reader could assume the gate protects something during start-up.

Suggestion

Confirm the intent. If the pair is left over from an earlier design, remove it and add a comment explaining the AwaitReady self-call.

Harness
untested Not covered by the harness yet (design, naming or API-surface issue).

I-28 · Admin packages are echoed to subscribers

lowdesign
Where
EVentNode.cs:109–111
What the code does

Every admin package is first forwarded with SendData(package) without excluding the sender. (The other half of this issue, a link handshake that exchanged four ListEvents and re-flooded EventAdded for each entry, was fixed in commit e5b2492: each side now sends one list.)

Why it matters

It's idempotent, so it isn't wrong, but it's wasteful and makes the admin flow harder to reason about.

Suggestion

Exclude the source when forwarding admin packages.

Harness
untested C14 confirmed the four ListEvents per link setup (8 frames); since commit e5b2492 it's two (4 frames). The admin-package forwarding that remains isn't measured separately.

I-29 · Dead, legacy or placeholder code

lowconsistency
Where
IComms.cs, IPostProcessor.cs, TypedEvent.cs, BinaryConvertibleProperty.cs, TCPClientConnection.cs, EVentIDs.cs:31, Event.csproj:14–16
What the code does
  • IComms, IPostProcessor and TypedEvent are not referenced anywhere. TypedEvent looks like an earlier attempt at typed events.
  • BinaryConvertibleProperty throws NotImplementedException and is unused.
  • TCPClientConnection is a pre-refactor client. Its Stop() sends "DisconnectClient", which the node doesn't handle (the admin ID is "DisconnectInterconnect"), and nothing in the codebase ever sends DisconnectInterconnect.
  • NOTESEvents.HandleEvent and LocalCallbackClient.CallFunction are unused. (NOTESEventDescriptor.ReturnType, which was always "void", became the return signature of typed functions in commit 6fb3c52.) (NOTESDescriptor.GetTypeStructure was removed with the type-graph rework.)
  • The Action<Package> “reply” argument of OnDataReceived is always a no-op.
  • The project file includes an empty Connections\NativeCall folder.
Why it matters

A newcomer can't tell which parts are live.

Suggestion

Delete them, or mark planned features with [Obsolete] or a TODO that says what they are for.

Harness
untested Not covered by the harness yet (design, naming or API-surface issue).

I-30 · Naming and namespace inconsistencies

lowconsistency
Where
PacakgeType.cs, IBinaryConvertable.cs, EVentNode.cs:573
What the code does
  • Two root namespaces are in use: EVent.* (for example EVent.CoreFunctionality.EVentNode) and Event.* (for example Event.CoreFunctionality.TypeSafeEVentNode), sometimes within the same folder. The project file is Event.csproj.
  • File names don't match their types: PacakgeType.cs holds PackageType; IBinaryConvertable.cs holds IBinaryConvertible.
  • IBinaryConvertible is an abstract class, although the I prefix suggests an interface.
  • Typos: HandleFucntionDrop, EVentTCPConenctionBroadcastPort, SendRepply, "braodcast handshake".
  • BinaryConvertibleFloat exposes a public field value where the other primitives have a property Value.
  • Several files have a stray using static System.Runtime.InteropServices.JavaScript.JSType;.
  • Separate static ID counters in QueuedClient and LocalCallbackClient mean IEVentClient.ID is not unique within a process.
Why it matters

Discoverability suffers: users need both using EVent... and using Event... (see the Examples), and IntelliSense searches miss things.

Suggestion

Settle on one root namespace and fix the file names in one mechanical pass.

Harness
untested Not covered by the harness yet (design, naming or API-surface issue).

I-34 · Generic parameter order differs between registering and calling a function

lowconsistency
Where
LocalCallbackClient.cs:271, EVentNode.cs:443
What the code does

RegisterFunction<TInput, TResult> vs CallFunction<TResult, TInput>. The custom-serializer overloads also order their delegate parameters differently (Func<byte[], TInput, bool> vs Func<TResult, byte[], bool>).

Why it matters

This is easy to get backwards, and because both are IBinaryConvertible the compiler rarely catches it.

Suggestion

Use the same order in both (Func<TIn, TOut> style).

I-36 · Rough edges in the Examples

lowconsistency
Where
Program.cs:8–15, NodeB.cs:22–24, NodeC.cs:24
What the code does
  • while (true) { } busy-loops pin a CPU core per node.
  • NodeC's message says “Received from HubC over EVent via HubB then HubA”, but the data comes from NodeA via NodeB. “Hub” is also the old name for a node.
  • All nodes run in one process, which hides problems that only appear across processes (static counters, shared multicast port).
  • HubD is fully commented out.
Why it matters

These are the only runnable documentation, so they deserve polish.

Suggestion

Use Thread.Sleep(Timeout.Infinite) or Console.ReadLine(), fix the message, and allow selecting a node via args so each can run in its own process.

I-48 · Collection caps must match exactly (no narrowing, no compatible sizes)

lowdesign
Where
NOTESDescriptor.cs, NOTESFlexibleSerDes.cs
What the code does

A cap is part of the NOTES type and compared exactly. When a collection field is capped at registration (maxCount:) and its collection definition is capped too, the two must be equal; RegisterField throws otherwise. Across the network, Cat[<=8] and Cat[<=16] are simply different types.

Why it matters

A field can't narrow a reusable definition (a CatList capped at 16 used where a device can only take 8), and two nodes whose caps differ can't share an event even when every value one of them sends would fit the other. With platform-specific DTOs that's likely to come up.

Suggestion

Parked by the project owner for a later discussion. Options: allow a field cap only to narrow its definition's cap (the smaller one wins); and/or let agreement accept a sender whose cap is at most the receiver's. Either needs a rule for which side's cap goes into the agreed signature.

Harness
confirmed U11: a field cap of 5 on a collection definition capped at 3 is refused; 3 is accepted. N36 N39: capped and uncapped are different types.

I-24 · The name of NOTESEventDescriptor.Wins suggests the opposite of its effect

infounclear
Where
NOTESEventDescriptor.cs:61–64, TypeSafeEVentNode.cs:72–80
What the code does

Wins(other) returns true when this (the stored proposal) has the smaller RandomWeight. But when the stored proposal “wins”, TryInitiate replaces it with the incoming one and tells the newcomer to proceed (0).

Why it matters

In effect, the proposal with the larger random weight wins. That is a valid tie-breaker, but the name says the opposite, and it's unclear whether this is intended. Since signatures became canonical (sorted, commit e2e550c), competing equal proposals are identical, so which one wins no longer affects the wire. Only the confusing name remains.

Suggestion

Confirm the intended semantics, and rename (for example LosesTo) or invert the condition.

Harness
untested Not covered by the harness yet (design, naming or API-surface issue).

I-32 · Wire order is 'leaf fields first, then children', whatever the registration order

infoundocumented
Where
NOTESDescriptor.cs:21–39, NOTESDescriptor.cs:136–148
What the code does

RegisterField sorts each registration into fields (leaf types, whose own descriptor is empty) or children (composites). ToBytes writes all fields before all children. A type counts as a leaf if and only if it registered nothing, so a composite type that forgets to register its members silently becomes a “leaf” whose ToBytes is used directly.

Why it matters

For example, EVentFunction registers Handle, Parameters, ReturnValues but is serialized as Parameters, ReturnValues, Handle. The order is deterministic, but surprising if you're implementing the protocol on another platform.

Suggestion

Document the rule (this wiki does, on the Wire format page), or keep a single ordered list.

Harness
confirmed U03: Household and EVentFunction serialize leaves before children.

I-33 · NOTES type identity is nominal on the root Name, and structural below it

infodesign
Where
NOTESDescriptor.cs:163–174, TypeSafeEVentNode.cs:200
What the code does

The signature is built with the root object's Name as the prefix ("Cat.Name:string"). The C# class name, namespace and declaration order play no part.

Why it matters

This is presumably intended, since it's what lets CatDescriptor and CatDescriptorReordered interoperate. But it also means that (a) changing a type's Name breaks compatibility with every running node, (b) two unrelated types that share a Name and field set are interchangeable, and (c) field names are the registration strings, not the C# property names (CatName is registered as "Name").

Suggestion

Worth stating explicitly as part of the NOTES contract.

untested Not covered by the harness yet (design, naming or API-surface issue).

I-37 · dRPC result semantics are under-specified

infounclear
Where
EVentNode.cs:557–572, EVentNode.cs:595–624, EVentNode.cs:464–476
What the code does
  • Results carry no responder identity, and arrive in no guaranteed order.
  • Results that fail to deserialize are silently dropped, so “3 of 4 answered” looks the same as “3 exist”.
  • Handlers that return null or an empty byte array count as “no answer”. This is why NOTESVoid is serialized as one byte.
  • The OnFunctionCall hook runs at every hop, for every function including NOTES' internal ones, and can replace the aggregated result. Its intended use isn't documented.
Why it matters

Callers can't tell a partial answer from a complete one, or who answered what.

Suggestion

Decide and document the contract. You could optionally include a responder ID and a count of the nodes asked.

Harness
untested Not covered by the harness yet (design, naming or API-surface issue).

I-38 · Nodes have no network identity

infounclear
Where
EVentNode.cs:14, TypeSafeEVentNode.cs:343
What the code does

NodeID is used only in debug output and the probe node's name. It is never sent over the wire. All addressing is by EventID and interest. There is no “send to node X”, no way to list the nodes, and no loop detection by ID (by design; see Topology rules).

Why it matters

This may be deliberate (pure publish/subscribe), but it limits diagnostics and makes cycle detection impossible.

Suggestion

If it's deliberate, say so. Otherwise consider including the node ID in the handshake.

Harness
untested Not covered by the harness yet (design, naming or API-surface issue).

I-45 · Raw event callbacks are delivered out of order

infoundocumented
Where
LocalCallbackClient.cs:71–77
What the code does

Each raw event callback is dispatched with its own Task.Run.

Why it matters

C15: 20,000 events from one publisher, all delivered, but up to 7,252 of them out of order, varying by run. Consumers can't assume ordering even from a single source.

Suggestion

Document it, or dispatch per subscriber serially (one queue per callback).

Harness
confirmed C15.

I-50 · Loops through policy layers are not detected

infodesign
Where
EVent/Policy/FilterLink.cs, EVent/Policy/NamespaceLink.cs
What the code does

Firewall and namespace nodes block the merge control functions (NOTESMergePing, StopEvents, AllowEvents) unless PassMergeControl / passMergeControl is set, so a merge on one side neither sees nor freezes the other.

Why it matters

Two networks joined through two policy layers (or one and a plain link) form a loop that TryEstablishConnection can't see; an event allowed both ways then circulates.

Suggestion

Join two networks through one policy layer, or pass merge control where a loop is possible. A loop check that crosses the layer without giving the far side the freeze would close the gap.

Harness
untested Documented on the firewall page; F11 checks that merge control crosses only when asked.

I-51 · Scripts run with the full rights of the scripting node's process

infodesign
Where
EVent.Scripting/ScriptCompiler.cs, EVent.Scripting/ScriptingWebHost.cs
What the code does

Scripts are compiled against the whole framework and run in the node's process; .NET has no sandbox. The page listens on 127.0.0.1 only, needs a per-start token, and refuses requests whose Host or Origin isn't local.

Why it matters

Whoever can reach the page with its token can run any code the process may run. A script that never finishes can't be stopped, only abandoned.

Suggestion

Run the scripting node as its own process with minimal OS rights; optionally check the symbols a script uses against an allow-list at compile time, and put a firewall node in front so scripts reach only chosen endpoints.

Harness
untested X06 checks the token and Host checks; the sandbox question is by design.
