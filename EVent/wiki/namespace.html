Namespace node

Turns a network into a named sub-network: it exposes its own events and functions as ns.Value, and sees only the outside names it imports.

A NamespaceNode (NamespaceNode.cs) is built like the firewall node: two full TypeSafeEVentNodes, Inner and Outer, joined by a link (NamespaceLink.cs) over which they run the normal link protocol. Instead of filtering, the link renames: every event or function X of the inner network exists in the outer network as ns.X, and an outer node that fires, hooks, registers or calls ns.X reaches the inner X. It works in both directions, for events and for functions.

What is renamed

The link renames by the direction a package travels: wrapping going out (X becomes ns.X) and unwrapping coming in (ns.X becomes X). Nothing inside a payload is read or changed, so no (de)serialization happens on the way.

What crossesHow it is renamed
Data packages, and an application's own admin eventsThe package's event ID.
A function call (a typed event is one too)The package's ID and the ID of the call's parameters inside it, which the receiving node checks.
The answers to a callEach answer's ID, on the way back: an answer to an outer call of ns.X leaves the inner side as X and arrives as ns.X.
Interest: EventAdded, EventRemoved, the event listsThe announced ID, so a subscriber on one side is seen under the right name on the other. An ID that can't be spelled on the other side isn't announced.

Building one

var kitchen = new NamespaceNode("KitchenGate", "kitchen",
    new TCPServer(IPAddress.Any, 5710, "KitchenInside"),     // inner: the network whose events get the name
    new TCPServer(IPAddress.Any, 5711, "KitchenOutside"));   // outer: where they appear as kitchen.X

kitchen.Inner.TryEstablishConnection(kitchenNetworkInfo);
kitchen.Outer.TryEstablishConnection(houseNetworkInfo);

// In the kitchen network:
oven.HookEvent("Preheat", (Temperature t) => ...);
oven.RegisterFunction("Status", (NOTESVoid _) => new OvenStatus(...));

// In the house network:
house.FireEvent("kitchen.Preheat", new Temperature(200));              // reaches the oven
var answers = house.CallFunction<OvenStatus, NOTESVoid>("kitchen.Status", NOTESVoid.Void);

Qualify("X") gives ns.X. A namespace may itself contain dots (house.kitchen); it must be non-empty, without whitespace or control characters, must not start with $, and its parts must be non-empty (otherwise ArgumentException).

The boundary

  • Exports (inner to outer): every ID of the inner network is reachable outside, under the namespace (X becomes ns.X). The namespace announces them as one prefix route, ns.*, not one by one.
  • Imports (outer to inner): names of the outer network the namespace declares it uses, spelled as the outer network spells them: a namespace such as World (covering World.Time and everything under it) or a single ID. Each is announced inside as one prefix route (World.*). They keep that spelling inside and cross both ways unchanged, so inner nodes call, fire, hook and provide them exactly as if they were in the outer network. World matches World.Time but not WorldEdit.
  • Nothing else comes in. Any other ID of the outer network is invisible to the inner side: no interest, no calls, no data, and it can even have a different type there (harness S04, S11, S15). An inner network's routing tables therefore hold its own IDs plus one entry per import, however large the outer network is.
  • One to one. An import may not be the namespace itself or lie under it, and an outer ns.X whose X reads as an import doesn't come in, so every ID has exactly one spelling on each side. An imported ID is never re-exported as ns.X.
  • $ is reserved. An ID whose name starts with $ belongs to the node itself and never crosses (ns.$Describe is one).
  • Protocol IDs. The IDs the type agreement and merges use for themselves aren't events and are not renamed. The descriptor functions cross with their payloads renamed; the merge control functions (NOTESMergePing, StopEvents, AllowEvents, AwaitReady) cross only with the passMergeControl constructor argument, exactly as in the firewall. An outer ID such as ns.AwaitReady is not allowed to name one of them.

A namespace node applies no policy beyond that. To restrict what may cross, put a firewall node on either side of it: the two compose because each is just a node in the network next to it.

Routing: one entry per namespace

The two sides exchange their event lists when the link comes up, and the link rewrites them: outward it adds ns.* and leaves out every exported ID, inward it adds one imp.* per import and leaves out every ID under an import. So the outer network holds one routing entry for the whole namespace (plus the namespace node's own ns.$Describe), however many endpoints are inside and however deep the tree goes; S16 puts 50 functions inside and finds exactly kitchen.* and kitchen.$Describe one hop out. Nested namespaces are covered by their parent's route: Minecraft.* carries Minecraft.Player.Health to the Minecraft namespace, whose network routes Player.Health on its Player.* entry.

What still crosses by name is a subscription to one specific ID: an outer node that hooks ns.X (it wants the inner publisher's X events) is announced inside as X, and an inner node that hooks an imported event is announced outside. Those entries exist only along the path that needs them.

The trade-off: behind a prefix route, the outer network no longer knows which IDs exist. A call or event for an ID nobody inside handles travels to the namespace and is answered there with nothing. It completes at once, not after a timeout, because the inner node knows it has no providers. A typed FireEvent or CallFunction first asks the network for the ID's agreed type; if no node has one and the ID is routed only by a prefix route, it is treated as having nobody interested (FireEvent returns true, CallFunction no answers) instead of as a type mismatch (S16).

Types across the boundary

Renaming would silently cut the type agreement in two (the outer network would never learn the inner types), so the descriptor traffic is renamed like everything else: a proposal for ns.E reaches the inner side as a proposal for E, a query for ns.E is answered with E's descriptor relabeled ns.E, and so on. The relabeled descriptor keeps its type and its random weight, so an abort still finds the proposal it withdraws. The result is that the type is the same under both names:

  • An outer node that hooks ns.E with a type that differs from the inner E's is refused (HookEvent returns false), and so is the inner node hooking E with a type that differs from the outer ns.E (S02).
  • A network that joins later learns the types that were agreed before, under the new name (S08).
  • IDs outside the namespace keep independent types on each side (S11).
Where type safety is not kept

The layer never looks inside a payload, so it can only keep the type safety that NOTES has agreed. Untyped events (raw Data packages) have no type to check; a type is only compared once one side has agreed one; and an event the outer network already uses as ns.E with its own subscribers shares the ID with the inner E, so both sets of subscribers receive what is fired. That is the price of the namespace being a name, not a separate space.

Namespaces as sub-networks

Namespaces nest by chaining: join the Outer of one namespace node to the network inside another. An X in the innermost network is b.X one level up and a.b.X two levels up, with its type checked across every boundary and calls answered back through all of them (S07). Imports connect namespaces sideways and upward: a namespace imports what its parent network calls a name, and the parent may itself have imported it from further out. The result is a tree of sub-networks, each of which exposes its own names and uses only what it declares. Harness S14 builds this one:

// global network --[ Minecraft, imports Server ]-- Minecraft network --[ Player, imports World, Server ]-- player network
//                                                                     \-[ World ]-- world network
var minecraft = new NamespaceNode("MC", "Minecraft", mcInside, mcOutside, imports: new[] { "Server" });
var player    = new NamespaceNode("PL", "Player", plInside, plOutside, imports: new[] { "World", "Server" });
var world     = new NamespaceNode("WO", "World", woInside, woOutside);

minecraft.Outer.TryEstablishConnection(globalInfo);
player.Outer.TryEstablishConnection(minecraftInsideInfo);   // Player and World live in the Minecraft network
world.Outer.TryEstablishConnection(minecraftInsideInfo);

// In the player network, with local names:
playerNode.RegisterFunction("Health", (PlayerName who) => (BinaryConvertibleInt32)HealthOf(who));
var time = playerNode.CallFunction<NOTESVoid, BinaryConvertibleInt32>("World.Time", NOTESVoid.Void);   // a sibling, via the import
var tps  = playerNode.CallFunction<NOTESVoid, BinaryConvertibleInt32>("Server.Tps", NOTESVoid.Void);   // global, imported twice

// In the global network:
var hp = globalNode.CallFunction<PlayerName, BinaryConvertibleInt32>("Minecraft.Player.Health", steve);

What each network's routing tables hold, beyond its own IDs (S14): the global network Minecraft.* and Minecraft.$Describe; the Minecraft network Player.*, World.*, Server.* and the two nested $Describe functions; the player network World.* and Server.*; the world network nothing from outside (it imports nothing, so its Server.Tps call gets no answers). Unrelated global traffic reaches none of them. Types hold across the whole chain: a Dog fired at Minecraft.Player.Damage is refused.

A namespace can contain dots (house.kitchen); one node with the namespace a.b gives the same names as two chained nodes, without the middle network.

Discovery

Namespaces describe themselves over the network, as typed NOTES records, so a program, a UI or a script gets the same structure, and JSON is just one rendering of it. Two functions do it, both on the namespace node's outer side and both starting with $, so they never cross a namespace boundary:

FunctionAnswers
$Namespaces (NamespaceNode.NamespacesEventID), NOTESVoid → NamespaceSummaryEvery namespace node answers it in the network its outer side is in, so one dRPC call returns one answer per namespace of the caller's network: from the top, the top-level namespaces; from inside Minecraft, Player and World; from inside a namespace with none nested, nothing. A summary is the name, imports, nested namespaces and endpoint count (S17).
ns.$Describe (DescribeEventID), string → NamespaceDescriptionOne namespace in full: its imports, its nested namespaces (found from their prefix routes), and every endpoint, an ID some node inside handles, with its agreed type, or untyped if none is agreed (raw events). The string is a prefix filter on the inner ID; empty lists everything.

NamespaceDirectory

NamespaceDirectory (EVent/Policy/NamespaceDirectory.cs) wraps both for any typed node, and walks the tree:

var dir = new NamespaceDirectory(node);

IReadOnlyList<NamespaceSummary> namespaces = await dir.ListAsync();          // $Namespaces
NamespaceDescription? mc  = await dir.DescribeAsync("Minecraft");             // Minecraft.$Describe
NamespaceTree? tree       = await dir.DescribeTreeAsync("Minecraft");         // and everything nested, recursively
IReadOnlyList<NamespaceTree> all = await dir.DescribeAllAsync();               // every namespace of this network
string json               = await dir.DescribeAllJsonAsync();                 // the same, as one JSON document

EndpointDescription? hp = await dir.DescribeEventAsync("Minecraft.Player.Health");
// hp.IsFunction == true, hp.InputType == "string", hp.ReturnType == "int32", hp.Input = the full NOTES signature

DescribeEventAsync doesn't list anything: it asks the whole network for the agreed type of one ID by its full name, and the question is renamed on its way through each namespace like any type agreement traffic (S18). From inside a namespace, imported names work too: in Player, DescribeAsync("World") and DescribeEventAsync("World.Time").

Endpoints carry the documentation they were agreed with: a Description, and per record an Annotations object with each documented field's description, range and default (see Documenting fields; harness S19). In the JSON, an optional record member is described under Children with "Optional": true, and a record reached only through a collection (Cats: Cat[]) is described once under a Records object next to the root, so every record of a type is spelled out.

A namespace node spells names as its own outer network does (Player.Health), and payloads are never renamed in transit, so the directory respells each answer for the asker: reached as Minecraft.Player, its endpoints read Minecraft.Player.Health and its import World reads Minecraft.World. Every name in the results can be used as it is, from the node that asked.

RecordFields
EndpointDescriptionId, Kind (event, function, untyped), Description, Input and Returns (canonical NOTES signatures), InputAnnotations and ReturnAnnotations; helpers InputAnnotation(record, field), ReturnAnnotation(record, field), helpers IsEvent, IsFunction, IsTyped, InputType, ReturnType, ToJson().
NamespaceDescriptionNamespace, Imports, Namespaces, Endpoints; ToJson().
NamespaceSummaryNamespace, Imports, Namespaces, EndpointCount.
NamespaceTreeDescription, Children, Unreachable (nested namespaces that are routed but didn't answer), AllEndpoints; ToJson(). Built locally, not sent.

The same pieces work on their own: NOTESSignatureJson.ToJson(signature) turns a signature into this JSON shape (the shape NOTESDescriptor.ToString() prints for a live type, plus a Type for the root; S10), NamespaceNode.Describe() and Summarize() build the records locally, and DescribeJson() renders one.

Example: one application using another's API

Application A runs EVent internally with five endpoints and publishes three. A firewall node lets only those three come in, and a namespace node names them ApplicationAPI.* on a shared bus. Application B is a namespace too, ApplicationB, and imports ApplicationAPI. Harness S13 runs this end to end.

// Application A: five endpoints in its own network, three of them public.
service.RegisterFunction("GetStatus", (BinaryConvertibleString detail) => Status(detail));
service.RegisterFunction("Convert", (Cat c) => Convert(c));
service.HookEvent("Submit", (Cat c) => Queue(c));
service.HookEvent("AdminReset", (Cat c) => Reset());              // private
service.RegisterFunction("InternalAudit", (Cat c) => Audit(c));   // private

var gate = new FirewallNode("Gate",
    new FirewallPolicy(DirectionRule.Block, DirectionRule.Whitelist("GetStatus", "Submit", "Convert")), gateIn, gateOut);
var api  = new NamespaceNode("Api", "ApplicationAPI", apiIn, apiOut);

// Application B: a namespace of its own that uses ApplicationAPI.
var b = new NamespaceNode("B", "ApplicationB", bIn, bOut, imports: new[] { "ApplicationAPI" });

service.TryEstablishConnection(gateInInfo);          // A's network -> firewall
gate.SideO.TryEstablishConnection(apiInInfo);        // firewall -> A's namespace
api.Outer.TryEstablishConnection(busInfo);           // both namespaces join the shared bus
b.Outer.TryEstablishConnection(busInfo);
appB.TryEstablishConnection(bInInfo);                // B's application joins its namespace

// Inside application B:
var status = appB.CallFunction<BinaryConvertibleString, Cat>("ApplicationAPI.GetStatus", "uptime");   // works
appB.FireEvent("ApplicationAPI.Submit", order);                                                       // works
appB.CallFunction<Cat, Cat>("ApplicationAPI.InternalAudit", x);   // no answers: it doesn't exist from here
var docs = await new NamespaceDirectory(appB).DescribeAsync("ApplicationAPI");

What S13 checks: B's network knows exactly ApplicationAPI.GetStatus, .Submit, .Convert and .$Describe, and nothing else from the bus; the bus knows those plus B's own exports, and nothing of either application's internals; the calls and the event work with answers and acknowledgements coming back through both namespaces and the firewall; the private endpoints can't be seen or reached from B but still work inside A; a call with the wrong input type is refused; and ApplicationAPI.$Describe, called from inside B, lists the three.

Faults and stopping

Same as the firewall: Stop (or Dispose) stops both nodes and the link and is safe to repeat; OnLinkLost is raised if the link closes without it; OnBlocked reports packages the link refused (for example a call for an ID that can't be named on the other side, which is answered at once with an empty return); ForwardedCount and BlockedCount count them (S12).

Limits

  • One namespace per node; nest by chaining.
  • The namespace and the imports are fixed at construction.
  • An import is a shared name: an inner node that provides an imported ID becomes one more provider of it in the outer network. Put a firewall in front of the namespace if that must not happen.
  • Behind a prefix route, calls for IDs that don't exist travel to the namespace before they are answered with nothing (see Routing).
  • A name is a prefix, not a separate space (see the note under Types across the boundary).
  • Payloads are opaque: a value that contains an event ID is not renamed.
