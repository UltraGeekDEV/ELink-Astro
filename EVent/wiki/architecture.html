Architecture

How EVent is layered, which class does what, and how data and threads move through it.

Purpose and design goals

According to the project description and the code, EVent aims to be:

  • Heterogeneous. A node can use several transports at once (params ICommsProtocol[]). Links made over different media form one network, so a serial-attached device and a TCP-attached PC can share events.
  • Address-free. Code never names a peer. It names an event (a string), and the network works out who cares about it.
  • Two interaction styles. Direct events (multicast to everyone interested) and dRPC, a scatter/gather query to everyone who can answer.
  • Typed without per-message overhead. NOTES negotiates a canonical layout per event, so payloads are plain concatenated bytes.

Layers

The key design decision (commit d38b562: “now EventNode handles inter node comms, and local callbacks are just an other client”) is that the router, EVentNode, treats your in-process code exactly like a remote peer. Both implement IEVentClient (Send / ReadPackage / Shutdown). That's why the same routing, interest propagation and dRPC aggregation logic serves local and remote subscribers alike.

A network of nodes

A network (the project description also says sub-network) is the set of nodes that are transitively linked. Nothing is centralised: every node keeps its own routing table, and changes spread through the network by flooding admin messages. See Links & interest routing.

Note

By design, the routing has no loop suppression, so the link graph must stay a tree: a link that closes a cycle makes announcements and data circulate forever. TypeSafeEVentNode.TryEstablishConnection refuses such a link with MergeResult.AlreadyConnected (Loop prevention). Raw EVentNode links are the caller's responsibility (Topology rules).

Which using directives?

Two root namespaces are mixed: EVent.* and Event.* (I-30). The main ones you'll need are Event.CoreFunctionality (TypeSafeEVentNode, LocalCallbackClient), EVent.CoreFunctionality (EVentNode, QueuedClient), Event.CoreFunctionality.EVentIDs (constants), EVent.Connections (ICommsProtocol, PackageType), EVent.Connections.TCP, Event.Connections.Serial, EVent.Connections.Models.BaseBinaryConvertibles (Package, primitives) and Event.Connections.Models.BaseBinaryConvertibles (NOTES types, NOTESVoid, EVentFunction).

How a message flows

A raw event

  1. Your code calls LocalCallbackClient.FireEvent("X", payload). Local subscribers on the same node are called directly on the thread pool.
  2. If some other client of the node has announced interest in X (tracked in NodeEvents), the payload is wrapped in a Package (PackageType.Data) and written to the local client's channel.
  3. The node's read loop for the local client picks it up. ProcessData calls SendData(package, source), which forwards it to every client interested in X except the source.
  4. Each remote QueuedClient queues the bytes, and its pump writes them to the socket or serial port.
  5. On the next node, the same thing repeats: it forwards to its own interested clients and raises OnDataReceived. Its LocalCallbackClient deserializes the payload and calls your callback.

A dRPC call

  1. EVentNode.CallFunction("F", input) creates an EVentFunction with a fresh handle and sends a FunctionCall package to every client interested in F, including the local client if it registered F.
  2. Each receiving node gives the call its own handle, forwards it to its interested clients except the sender, and remembers whom it is waiting for.
  3. Leaf responders (local clients with a registered function) run the function and append their result to ReturnValues.
  4. As the answers arrive (or links drop), each node merges the results. When nobody is left pending, it returns one aggregated FunctionReturn upstream.
  5. The original caller unblocks with a List<TResult> holding one element per responder in the whole network.

See Distributed RPC for the details and a sequence diagram.

A typed (NOTES) event

TypeSafeEVentNode.FireEvent is a dRPC call in disguise. Subscribing registers a function that returns NOTESVoid, and firing calls that function network-wide using a serializer that follows the agreed field order. See How EVent and NOTES fit.

Threading model

WhereWhat runs thereConsequence
Transport accept loopsTCPServer.Run starts a Task.Run that calls AcceptTcpClient (blocking). SerialServer.Run polls the port list every second.Inbound links call EVentNode.AcceptClient from these threads.
One read loop per clientEVentNode.RunClient (async void) awaits ReadPackage and calls ProcessData inline.Routing, forwarding and replies are handled here and never wait. Function handlers (typed-event callbacks included) are not: they're handed to the thread pool, so a slow handler never stalls its link.
One send pump per QueuedClientEmptyQueue drains a Channel<Package>.Raw events wait for room (MaxQueuedDataBytes); the node reads a link's raw events in order and waits for a full link downstream. Everything else is queued at once.
Thread poolRaw event callbacks and function handlers in LocalCallbackClient (a task per callback, and per call).Callbacks and handlers run concurrently and unordered. EVent doesn't guarantee delivery order.
Nowhere (async)CallFunctionAsync, HookEventAsync, FireEventAsync, TryEstablishConnectionAsync and the merge and agreement logic behind them complete when the network answers; nothing waits on a thread.Any number can be in flight. Each call gives up on the providers that haven't answered after FunctionCallTimeout (30 s by default, or a timeout passed per call), and every async form takes a CancellationToken.
Caller threadThe blocking forms (CallFunction, HookEvent, FireEvent, TryEstablishConnection) wait for their async form. TypeSafeEVentNode's constructor waits once, briefly, for its registrations to be routed.Fine from your own threads. Many blocked thread-pool threads slow the links down, because they read on the pool too (Threading).

Shared state is protected by clientLock in EVentNode, callbackLock in LocalCallbackClient and typeLocks in TypeSafeEVentNode. An ExecutionGate lets TypeSafeEVentNode pause every typed operation during a network merge. Some reads happen outside these locks (I-19).
