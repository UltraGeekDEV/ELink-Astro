Type agreement protocol

How nodes agree on an event's type, and how networks with typed events are merged safely.

All of this is in TypeSafeEVentNode.cs. Each typed node holds:

StateMeaning
establishedEvents: Dictionary<string, NOTESEventDescriptor>Descriptors this node believes the network agreed on.
potential: Dictionary<string, NOTESEventDescriptor>Proposals this node has accepted but that aren't final yet.
potentialExpiry: Dictionary<string, long>When each pending proposal expires (Environment.TickCount64 deadline). Set from ProposalTimeToLive, 5 s by default.
SerDesCollection: Dictionary<(string, Type), NOTESFlexibleSerDes>Cached serializers per event ID and C# type, so a node can hook and fire different compatible types for one event. Cleared for an event when a merge overrides its descriptor.
gate: ExecutionGatePauses HookEvent/FireEvent during merges.
typeLocksGuards the dictionaries in the handlers.

Start-up

  1. Create the inner EVentNode, subscribe to OnConnected, and start the transports.
  2. Close the gate, attach a LocalCallbackClient, and register the eight NOTES system functions on it. Each registration queues an EventAdded to the node.
  3. Open the gate, then call AwaitReady on the network every 10 ms until at least one answer comes back. The first answer is normally this node's own, which proves the local registrations have reached the router. (The purpose of the Close/Open pair is unclear, I-27.)

HookEvent: agreeing on a type

Algorithm

  1. Enter the gate.
  2. Build the NOTES description of T (NOTESFlexibleSerDes.For(new T())): its canonical signature and serializer. If NOTES can't describe the type (reserved characters, a name used for two structures, a type that contains itself directly), return false.
  3. Already established? Under the lock, compare the local signature with the established one. If they're identical, cache the serializer, register the callback as a function with it, and return true. On any difference, return false.
  4. Otherwise create NOTESEventDescriptor(signature, eventID, returns) (for HookEvent, returns is Void's signature) with a random RandomWeight and call TryInitiateNOTESDescriptor network-wide, including on this node.
  5. If all answers are 0: call FinalizeNOTESDescriptor(D) network-wide with the full proposal. If any node answers -1 (a different type is already established there), send AbortNOTESDescriptor(D) and return false. Otherwise check that the established descriptor is exactly the proposal, cache the serializer, register the callback as a function with it, and return true.
  6. If not all answers are 0: send AbortNOTESDescriptor(D) so every node that accepted D drops it. Then, if any answer is -1, it's a type mismatch: return false. If some node answered 2 (Established), an equal type was agreed before this node could see it, for example on the other side of a merge: fetch it with QueryDescriptors, store it, and go straight back to step 2, which now takes the already-established path. Otherwise (only 1s: an equal proposal that outranks ours is still pending) wait 100 ms and go back to step 2.
  7. Leave the gate.
Documentation rides along

A proposal also carries its proposer's endpoint description and field documentation (Description, InputAnnotations, ReturnAnnotations). They are not compared: two proposals that differ only there are equal, and whichever becomes the agreed descriptor brings its documentation with it. See Documenting fields.

Recovering from failed or interrupted agreements

Three mechanisms (commit 7e35633) make sure an agreement that doesn't complete never blocks an event ID permanently:

MechanismWhat it doesCovers
Finalize carries the proposalEach node commits exactly the proposal it's given and drops any other pending one for that event, whether or not it still holds the pending entry. It answers -1 only if a different type is already established.Nodes committing different proposals; slow Finalize after a pending entry expired.
AbortOn any non-success the proposer sends AbortNOTESDescriptor(D). A node removes its pending entry only if it is literally D (same type and random weight, IsSameProposal), so a competitor's proposal is never touched.Rejected and contested proposals. After two incompatible types collide, often both hooks return false, but nothing is left behind, so an immediate retry succeeds.
TTLA pending entry older than TypeSafeEVentNode.ProposalTimeToLive (default 5 s) is treated as absent. The check is lazy (on read), so no timers run.A proposer that crashes or loses its link between TryInitiate and Finalize: its proposal blocks competitors for at most the TTL.

“Equal” means NOTESEventDescriptor.Equals: same EventID, and identical input and return signature lists in the same order. Because signatures are canonical, two equal types always produce identical lists. With two competing equal proposals, the one with the larger random weight goes ahead, even though the method is called Wins (I-24). Since both proposals are byte-identical, it no longer matters which wins.

FireEvent

  1. Enter the gate.
  2. If this node has no agreed type for the ID: if nobody in the network routes it, return true (nobody is interested); otherwise fetch the descriptor with QueryDescriptors and adopt it. Then use the serializer cached for the ID and data's type, or build one, check that its signature equals the established one (input, and Void as the return), and cache it, all under the lock. If it differs, or the ID has no agreed type at all (raw subscribers only), return false: that's a type mismatch, the only case that returns false.
  3. Serialize data (TryToBytes). A null member or element, an exceeded cap or too-deep nesting returns false.
  4. Call network.CallFunction<NOTESVoid, T>(eventID, data, ...) with those bytes, which blocks until every subscriber's handler has returned.
  5. Return true: every interested party received it (possibly nobody).

Typed functions

RegisterFunction<TIn, TOut>(id, handler) and CallFunction<TIn, TOut>(id, input) are the same machinery with the answers kept. The algorithm above runs with TOut's signature as Returns instead of Void's. Because the descriptor's equality covers both signatures, every existing check applies to the pair unchanged: a pending or established pair with a different input or return type is a conflict (so an event and a function can't share an ID), and a merge where one side has another return type is refused with TypeConflict (N61, N62).

  1. Enter the gate.
  2. Find (or build, check against the established pair and cache, under the lock) the serializers for input's type and TOut. As with FireEvent, an ID nobody routes completes with an empty collection, an unknown but routed one is adopted first, and a mismatch returns null.
  3. Serialize input in the agreed layout; if it can't be, return null.
  4. Call network.CallFunctionAsync<TOut, TIn> with those bytes. Each provider decodes the input with its own serializer, runs its handler, and encodes the result in the agreed return layout; a null result (or one that can't be encoded) is sent as no bytes, which the core treats as no answer.
  5. Decode every answer into a TOut and return them as a BinaryConvertibleCollection<TOut>, one per provider that answered (N59).
Note

A node can fire an event it never hooked, as long as it knows the established descriptor. In the Examples, NodeA only fires TestA after its own HookEvent established it.

Merging two networks

TryEstablishConnectionAsync(Package connectionInfo) TypeSafeEVentNode.cs:560–640 links this node's network to another one, unless the link would close a loop, the other side doesn't run NOTES, or an event has conflicting types. It completes with a MergeResult once the real link is up; the blocking TryEstablishConnection returns true/false (and the result through out). Without contention a merge takes a handful of round trips: a few milliseconds in memory (N45, N48).

MergeResultMeaning
ConnectedNo loop, no conflicting merge in flight, descriptors aligned; the real link is up.
AlreadyConnectedOur merge ping came back through our own probe: the target already reaches us, so the link would close a loop.
TypeConflictAn event is established with a different type on the other side.
NotNOTESThe target's event list has no NOTESQueryDescriptorSet.
UnreachableNo transport could reach the target within MergeStepTimeout.
TimeoutA step of the merge didn't complete within MergeStepTimeout, MaxMergeAttempts times over: a node on the path died without its link dropping, or the target stopped answering.
BusyA merge in our way never ended: its number blocked ours for longer than any healthy merge takes (8 × MergeStepTimeout), so its node is taken as broken.

Loop prevention

Before anything is frozen, a temporary probe node dials the target and subscribes to NOTESMergePing. The target's answer to the probe's QueryEvents proves it has hooked that subscription. Nothing has to spread further: every typed node registers NOTESMergePing, so every path through typed nodes already routes merge pings toward the target, and the target routes them to the probe.

Then our node sets a random 64-bit merge number and calls NOTESMergePing once, on its own network. A node answers only with the numbers of its own merges in flight; a probe answers with its owner's number. Nobody keeps a record of anyone else's merge, so nothing can go stale, and a merge whose node dies simply stops being reported. The call completes only when every node in our group has answered, so the answer is complete. In the normal case (a small group joining a big network) the ping reaches only our group; the target's network never sees it.

Why one round is enough. Take two merges, A and B, in flight at once. Each sets its number before its ping leaves, and A's ping has to reach B's node (or B's probe) before it completes, and B's ping A's. For both to miss each other, A's ping would have to pass B before B set its number, and B's ping pass A before A set its number, but each set its number before its own ping left: the four moments would have to happen in a circle. So at least one of the two always sees the other, whatever the latency. The same holds for two groups linking into each other: each probe sits inside the other group, so it's reached by that group's ping.

The ping returnsMeaningReaction
Our own numberOur probe was reached through our own network: the target already reaches us.AlreadyConnected.
NothingNo loop, no other merge that could conflict.Go: freeze our group, check descriptors, link.
Other numbersOther merges are in flight (in our group, or into it from outside).Clear our number and back off, then ping again (below).

Contention. A merge that sees others steps aside: it clears its number (so nobody ever waits on it) and waits a random time before pinging again. As on a shared medium, the waiting window doubles every time it steps aside (binary exponential back-off, in units of its last ping round trip, capped at 32), so a crowd thins out quickly, while a merge that never meets another pays nothing. A merge that saw only numbers larger than its own draws from half the window, so lower numbers tend to go first. Whoever pings into a clear network goes; the rest then find either a clear way or their own number coming back (AlreadyConnected). With 20 merges started at once between 5 groups, the four that connect the network finish within about 3 s at 0–50 ms per link, and the result is always a tree (N55).

Timeouts. MergeStepTimeout (5 s) bounds each network step: reaching the target, its handshake, the ping, freezing our group, the descriptor query, the new link's handshake. Every step normally completes in a round trip, so the timeout only fires when a node on the path died without its link dropping, or the target stopped answering (N58). A timed-out step is never taken as clear: the merge clears its number, retries up to MaxMergeAttempts times, then returns Timeout. A merge whose node dies needs no timeout at all: its number disappears with it (N57). The only other bound is for a merge that never ends: a number that keeps blocking ours for longer than 8 steps' worth belongs to a broken node, and we give up with Busy (N46).

The handshake freezes only our group: StopEvents in our network, one NOTESQueryDescriptorSet call through the probe with every ID established here, refusal on any conflict. Nothing is adopted at this point: the target agrees on every event both sides know, and the rest travels over the link. Then the probe hands its connection over (EVentNode.DetachClient: it stops reading without closing the connection) and our node adopts it (AcceptClient(link, adopted: true): it sends InterconnectRunning and its event list straight away, because the target won't announce itself again). One connection, and one discovery round, per merge. When the target's list arrives the link is up: we clear our number and send AllowEvents. From then on our group's pings cross the new link, so a later merge in our group toward the same network finds its own number coming back.

After the link: OnConnected

When ListEvents arrives over a new link from a NOTES peer (its list contains NOTESShareDescriptors), each endpoint's OnConnected sends one network-wide NOTESShareDescriptors TypeSafeEVentNode.cs:246–282 call carrying every descriptor it knows. Each node commits the ones it lacks, with FinalizeNOTESDescriptor's rule (“commit if absent; a different type established here is a conflict”), and answers with the conflicting IDs. The other endpoint does the same, so nodes deep inside both sides learn each other's descriptors and can fire those events without hooking them (scenario N29). A plain peer, such as the merge probe, triggers nothing.

Before, each endpoint queried every ID in the peer's list one network-wide call at a time (NOTES system functions included), re-sent every descriptor one call at a time, and did all of it twice because every link exchanged its event lists twice. Now a merge costs the target network one probe query, two shares and the tail of AllowEvents, however many events there are.

The probe is always torn down, whether the merge is accepted or refused. It gives up after TypeSafeEVentNode.MergeStepTimeout (5 s by default). Nodes that know none of the asked IDs give no reply to NOTESQueryDescriptorSet, so nothing but real descriptors comes back (commit 56bab8b, scenarios N12, N16 and N31).

Caution

Limits of the loop check:

  • Only typed merges are checked. A raw EVentNode link can still close a cycle; by design, the core doesn't stop loops (Topology rules).
  • AllowEvents is sent after the real link is up, so it also reaches the target's network (14 frames in an 8-node chain), where it opens every gate, including any that a merge over there has closed at that moment.
  • The guarantee is about merges whose pings complete. If a link drops while a ping crosses it, the ping completes without the nodes behind it; a node you can't reach at that moment can't close a loop over that link either.
  • Under heavy contention, merges that end up AlreadyConnected can take a few seconds to find out, because they wait in back-off (silently) before pinging again.
