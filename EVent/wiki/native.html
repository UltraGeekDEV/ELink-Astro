C++ leaves

Programs in other languages join an EVent network as typed leaf nodes: one link to a router, their own NOTES implementation, no routing of their own. The C++ library in cpp/ is the first.

The router is an ordinary C# node, usually on the same machine: the interconnect between languages, machines and transports. A leaf talks to it over a byte stream (TCP on the loopback interface today; shared memory later, behind the same interface) and is a full participant in NOTES for its own endpoints: it takes part in type agreement, knows the network's agreed types, and checks every event and call against them in both directions. It never forwards anything and never merges networks; that is the router's job. Nothing listens on the C++ side: the leaf dials the router's ordinary TCPServer.

Building

The library is header-only C++17 (cpp/include/evn/); a program includes <evn/leaf.hpp> and links the platform's threads. With CMake:

add_subdirectory(path/to/cpp)             # the INTERFACE target evn: include path + Threads
target_link_libraries(my_app PRIVATE evn)

cpp/build.sh      # builds the self-test and the harness's peer tool into cpp/build, runs the tests

The first four are the portable core: C++17 without exceptions, I/O or threads (the self-test is built with -fno-exceptions), so an embedded implementation (ESP-IDF, later) can reuse them with its own shell.

Types

A struct becomes a NOTES record by mapping its fields once, next to it. The NOTES name defaults to the struct's name; EVN_RECORD_NAMED gives another (needed for a type in a namespace: EVN_RECORD_NAMED(app::Reading, "Reading", ...), placed in that namespace). Field order in the macro doesn't matter: the wire order is by name, as everywhere in NOTES. EVN_DOCS documents fields; the documentation travels with the types this program proposes and shows in every directory, exactly as RegisterField(...).Description(...).Range(...).Default(...) does in C#.

#include <evn/leaf.hpp>

struct Spot { int32_t Floor = 0; std::string Room; };
EVN_RECORD(Spot, Floor, Room)

struct Thermo {
    float Celsius = 0;
    std::optional<std::string> Label;          // optional: Label:string?
    std::optional<Spot> Where;
    std::vector<double> History;               // History:double[]
    evn::Capped<uint8_t, 16> Flags;            // Flags:uint8[<=16]
};
EVN_RECORD(Thermo, Celsius, Label, Where, History, Flags)
EVN_DOCS(Thermo, evn::doc("Celsius", "temperature in degrees Celsius").range(-40, 125),
                 evn::doc("Label", "sensor label").default_value("unnamed"))
// signature: =Thermo  Spot{Floor:int32,Room:string}
//            Thermo{Celsius:float,Flags:uint8[<=16],History:double[],Label:string?,Where:Spot?}

Any other integer type maps by size and signedness (long long is int64); plain char is refused, being signed on some platforms and not on others. evn::signature_of<T>(), evn::encode and evn::decode are there for tools and tests; decode is strict (short input, leftover bytes, a bool other than 0/1, an invalid decimal, an over-cap or lying count, nesting deeper than 64 all fail).

An application's own leaf type (like a C# class with no fields and its own bytes) is a Codec specialization:

struct Stamp { uint16_t Value = 0; };
template <> struct evn::Codec<Stamp> {
    static std::string ref(evn::Schema& s, int) { return evn::leaf_ref(s, "stamp16"); }
    static bool write(evn::Writer& w, const Stamp& v, int) { w.le(v.Value); return true; }
    static bool read(evn::Reader& r, Stamp& v, int) { return r.le(v.Value); }
};

The leaf

evn::Leaf leaf("sensor");
if (!leaf.connect_tcp("127.0.0.1", 5698)) return 1;          // the router's TCPServer port

auto hooked = leaf.hook<Thermo>("Home.Reading", [](const Thermo& t) { std::cout << t.Celsius << "\n"; },
                                "a room temperature reading");   // empty token: a type conflict
leaf.provide<evn::Void, int32_t>("Home.Count", [](const evn::Void&) { return 42; });
leaf.provide<Spot, std::string>("Home.Name", [](const Spot& s) -> std::optional<std::string> {
    if (s.Room.empty()) return std::nullopt;                  // no answer from this provider
    return s.Room + " on floor " + std::to_string(s.Floor);
});

bool ok = leaf.fire("Home.Reading", Thermo{21.5f});            // false only on a type mismatch
auto counts = leaf.call<int32_t>("Home.Count", evn::Void{});   // std::optional<std::vector<int32_t>>: one per provider
leaf.publish("Home.Reading", Thermo{21.5f});              // fire and forget: no acknowledgements, in order
leaf.remove(hooked);
MemberWhat it does
connect_tcp(host, port), attach(transport)Link to the router and wait for its handshake (handshake_timeout). With reconnect (default on), a lost link is dialed again every reconnect_delay; calling connect_tcp again meanwhile changes the target.
hook<T>(id, callback, description)Subscribe; agrees T as the type first if the network has none. Returns a Token, empty on a conflict.
provide<In, Out>(id, handler, description)Provide a function. The handler returns Out, or std::optional<Out> where nullopt gives no answer.
provide_async<In, Out>(id, handler)A provider that answers later: handler(const In&, evn::Answer<Out> answer), then answer(value) or answer.none() once, from any thread.
fire(id, value, options), call<Out>(id, input, options)Deliver to every subscriber / call every provider, here and in the network, and wait. fire is true also when nobody subscribed; call gives one answer per provider, empty if there are none, nullopt on a type mismatch.
publish(id, value)Fire and forget: hands the value to every subscriber (here and in the network) and returns without waiting for them. No acknowledgement travels and nothing is kept for the event, so streams of readings go several times faster than with fire. Events from one leaf reach a subscriber in the order published (a subscriber's handlers get one ID's events one at a time). It says nothing about the event having been handled: a router or subscriber that is gone, a link that breaks or a handler that throws loses it silently. True also when nobody subscribed; false on a type mismatch or when stopped. The router sees a FunctionCall whose call ID has bit 63 set (wire format).
fire_async, call_async<Out>The same without waiting: a std::future. Dropping it is fire-and-forget.
fire_then(id, value, done), call_then<Out>(id, input, done)The same with a callback, run like a handler.
hook_raw(id, callback), fire_raw(id, bytes)Raw (untyped) events: bytes as they are, no type checks, no waiting.
hook_dynamic, provide_dynamic, fire_dynamic, call_dynamicThe same with dynamic values instead of structs.
list(), type_of(id), known_types()The network's endpoints, like C#'s NetworkDirectory (namespaces expanded through their $Describe; raw-only IDs as "untyped"); one ID's agreed type (signatures, description, field documentation); the types this leaf knows.
remove(token)Drop a hook or function; the router stops routing the ID here when nothing else here handles it. The agreed type stays.
on_link(handler), connected(), router_handshake(), stop()Link changes; the router's handshake (implementation, protocol version); leave the network (also on destruction). A router with an incompatible protocol version is refused (and not re-dialed).

CallOptions carries a timeout (default call_timeout, 30 s) and an evn::Cancel: cancel.cancel() ends every call made with it now, as if its timeout had passed. A leaf without a link still works for its own endpoints (loopback), and types it agrees offline are offered to the network when it connects.

Asynchronous calls

for (auto& r : readings) leaf.fire_async("Home.Reading", r);          // fire-and-forget

auto pending = leaf.call_async<int32_t>("Home.Count", evn::Void{});    // std::future<std::optional<std::vector<int32_t>>>
// ... other work ...
auto counts = pending.get();

evn::Cancel cancel;
leaf.call_then<std::string>("Home.Name", Spot{2, "attic"},
    [](const std::optional<std::vector<std::string>>& names) { /* runs like a handler */ },
    evn::CallOptions(evn::Millis(2000), cancel));
cancel.cancel();                                                       // completes it now with what arrived

Blocking and asynchronous calls share one engine: the router's answer, this leaf's own handlers, a deadline and a cancel all complete the same call record, whichever comes first. The asynchronous path holds no thread while it waits, also not while it asks the network for an ID's type or waits out a merge freeze.

Where handlers run

By default (Dispatch::Threads) handlers and callbacks run on the leaf's handler threads, several at once (created on demand, at most max_workers, 64): make them thread-safe. Dispatch::Poll runs them on the application's own thread instead, inside poll(), for GUIs, games and event loops:

evn::LeafOptions options;
options.dispatch = evn::Dispatch::Poll;
options.wakeup = [&] { loop.post_wakeup(); };     // called from any thread when work is waiting (optional)
evn::Leaf leaf("game", options);
// ...
while (running) {
    leaf.poll();                                   // runs waiting handlers and callbacks here
    render();
}

The leaf's own protocol work (type agreement, the merge freeze) stays on its threads, so a busy application never stalls the network. In poll mode a blocking fire or call from the polling thread runs this leaf's own handlers inline; but it can't answer a call from the network while it waits, so prefer the asynchronous forms there. A handler that throws gives no answer.

Dynamic types

A program that meets types at run time (a logger, a bridge, a tool) uses dyn::Value: records by field name, lists, numbers, strings, with the network's agreed type deciding the bytes. Values convert from and to JSON in the NON shapes.

leaf.hook_dynamic("Home.Reading", [](const evn::dyn::Value& v) {
    std::cout << evn::dyn::to_json(v) << "\n";           // {"Celsius":21.5,"Where":{"Floor":1,"Room":"den"}}
});
evn::dyn::Value r;
r["Celsius"] = 19.5;
r["Where"]["Room"] = "attic";                            // missing required fields or unknown ones: refused
r["Where"]["Floor"] = 2;
leaf.fire_dynamic("Home.Reading", r);
auto sums = leaf.call_dynamic("Lab.Sum", *parsed_json);  // std::optional<std::vector<dyn::Value>>
// proposing a type from a signature (any order; agreed in canonical form):
leaf.provide_dynamic("Shop.Order", echo, {"=Order", "Order{Item:string,Note:string?,Qty:int32}"},
                                         {"=Order", "Order{Item:string,Note:string?,Qty:int32}"});

Numbers convert like NON's: an integer into any integer field it fits, any number into float, double and decimal, never a fraction into an integer; a one-character string into char16. A custom leaf needs dyn::register_leaf(name, step_over) and is held as its raw bytes.

The leaf protocol

What a leaf does on the wire, for implementing one in another language. Frames and layouts are those of the wire format; payloads of the protocol's own messages are in the plain layout, application values in the NON layout.

  1. Link. Open the byte stream to the router and send InterconnectRunning (ServerAdminEvent) with the handshake: int32 protocol version, int32 oldest version accepted, string implementation (the C++ leaf sends 1, 1, "evn-cpp"). The router sends its own; if its version is outside the leaf's range (or its payload is empty, version 0), send a LinkFault naming both and close. Otherwise answer it (and any QueryEvents) with ListEvents: a plain collection of strings, the leaf's interest. The router's ListEvents is its interest: the IDs it routes onward (names and prefix routes A.*). The link is up once it arrived.
  2. Interest. The IDs the leaf handles (typed or raw), plus the NOTES functions it answers (below). Send EventAdded / EventRemoved (a string) when an ID gains its first or loses its last handler; apply the router's to its interest set. After an EventAdded, call AwaitReady (it travels behind the notice): once it completes, the whole network routes the ID to the leaf.
  3. Calling. A typed event is a call whose providers answer nothing. To call ID X: if the router routes X (by name or by a covering prefix route), send a FunctionCall frame with an EVentFunction (Parameters: the frame X/FunctionCall/input; ReturnValues: empty; Handle: an ID of the leaf's choosing); run the leaf's own handlers of X too; the router answers once, with a FunctionReturn carrying the same Handle and every other provider's answers. A call waits at most its timeout; a link that drops completes it with what arrived.
  4. Answering. Answer every FunctionCall from the router with a FunctionReturn: the same EVentFunction (same Handle, same Parameters) with one Package(X, FunctionReturn, answer) per non-empty answer in ReturnValues. Always answer, even with nothing: the network waits for it.
  5. Raw events are Data frames: send one if the router routes the ID; deliver incoming ones to the raw subscribers. Nothing is answered.
  6. Types. Answer the NOTES functions like a .NET node (table below). To use an ID: if its type is known, the local types must match it; otherwise propose (below). Before sending, a leaf that doesn't know the ID's type asks QueryDescriptors and adopts the answer; nobody interested means nothing to check.
  7. Proposing. Call TryInitiateNOTESDescriptor with a descriptor (input signature, ID, answer signature, a random weight 0…231-2, description, field annotations). All replies 0 (accepted): call FinalizeNOTESDescriptor; any -1 there: AbortNOTESDescriptor and fail. Otherwise abort, then: a -1 (conflict) fails; a 2 (established) means fetch the type with QueryDescriptors and adopt it if equal; else (1, pending) wait 100 ms and start over. The leaf's own responder answers its own proposal too (loopback), which is what makes an offline leaf agree with itself.
  8. After the handshake, if the router's list contains NOTESShareDescriptors and the leaf knows types, call it with all of them: the network commits those it lacks. The router does the same towards the leaf.
  9. Malformed input (a bad frame or protocol payload): send LinkFault with the reason and close the stream.

Descriptors compare by ID, input and answer signature; description, weight and field documentation don't count. A leaf never answers NOTESMergePing: it has no merges of its own. Listing the network is built from the same pieces: the router's interest, NOTESQueryDescriptorSet for the IDs routed by name, and each namespace's ns.$Describe (a typed function answering EVentNamespace) for prefix routes.

Tested

Harness group Y runs C# routers with C++ leaves in separate processes (the evn_leaf_peer tool, scripted over stdin; values cross as hex of their NON bytes, so both sides compare bytes):

  • Y01: the self-test; signatures and bytes identical to .NET for 14 values of 12 types (every primitive at its edges, optional, nested, list, recursive, capped, a custom leaf); bytes .NET refuses are refused.
  • Y02–Y03: events and calls both ways, byte-identical; one call answered by a C# and a C++ provider together; a type defined in C++ binds C# classes; wrong types refused on both sides.
  • Y04: loopback offline; types agreed offline reach the network on connecting; removing a hook withdraws its route.
  • Y05: two leaves through one router; concurrent proposals never agree two types.
  • Y06: a leaf behind a namespace; a merge with a leaf attached (it answers the freeze); a router restart, after which the leaf re-dials and re-shares its types.
  • Y07: 2000 calls each way over loopback TCP, from 8 threads (about 14,000–22,000 calls/s on the test machine).
  • Y08: list() gives exactly C#'s NetworkDirectory (namespace endpoints, a raw-only ID, the leaf's own).
  • Y09: 1000 fire-and-forget events, futures and callbacks, a slow call cancelled after 100 ms, a provider answering 300 ms later.
  • Y10: Dispatch::Poll: handlers and callbacks on the main thread, woken through the wakeup hook.
  • Y11: field documentation identical whichever language proposed the type.
  • Y12: dynamic values: a C# type read as JSON, one fired from JSON, wrong shapes refused, calls, a provider proposed from a signature, a custom leaf.
  • Y13: raw events both ways, and back to the leaf's own raw hook.
  • Y14: the versioned handshake: the leaf refuses a router speaking protocol 99 with a LinkFault, and reports a current router's handshake.

See Test harness & results.

Limits

  • Windows: TcpTransport has a Winsock implementation, but it hasn't been compiled or run yet (no Windows toolchain where this was written).
  • A default in the field documentation is documentation only on the C++ side: an absent optional field reads as nullopt (C# reads it as the default).
  • Hooking and providing (type agreement, then confirming the route) block the calling thread; the network answers within a few round trips.
  • A provide_async handler must answer before the leaf stops.
  • Names are compared by byte order in C++ and by UTF-16 order in .NET; they agree for all but some non-ASCII names, so keep record and field names ASCII.
  • The embedded implementation, embedded routers (ESP-NOW and other transports) and the shared-memory transport are separate work that will reuse the portable core.
