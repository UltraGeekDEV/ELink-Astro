Wire format

Byte-level layout of everything EVent sends, for debugging and for other-platform implementations.

All multi-byte integers are little-endian, except the port inside the discovery handshake. Strings are UTF-8. Nothing carries tags or type information; the layout is implied by the EventID and, for typed events, by the agreed NOTES descriptor.

Package frame

Example: new Package("Ping", PackageType.Data, (BinaryConvertibleInt32)42) is 17 bytes:

0D 00 00 00   length = 13  (4 idLen + 4 "Ping" + 1 type + 4 payload)
04 00 00 00   idLen  = 4
50 69 6E 67   "Ping"
01            PackageType.Data
2A 00 00 00   int32 42

Package.ReadPackage(Stream) reads the length, rejects negative lengths and lengths above MaxPackageSize - 4 by returning null (which closes the link), reads the rest, and parses it. ToBytes throws ExcessivePackageSizeException when a package would exceed the limit.

Composite types (NOTESDescriptor)

A composite type serializes as the concatenation of its registered members, with no separators or names. NOTESDescriptor.ToBytes NOTESDescriptor.cs:136–148 writes all leaf fields first (in registration order), then all children (in registration order), recursively. Registration order is only preserved within each group (I-32). Whether a member counts as a record is decided when serializing, not at registration, so mutually recursive types get the same layout whichever static constructor ran first (harness U13/U14). An optional member is preceded by a presence byte, as in the NOTES layout.

That's the layout used by the core's own composite types, and by raw LocalCallbackClient events whose payload is a composite type. Typed NOTES events use a different layout: the canonical one (next section).

EVentFunction (dRPC envelope)

Registered as Handle, Parameters, ReturnValues, but Handle is a child (it has its own fields), so the bytes come out in this order:

#MemberEncoding
1ParametersNested Package: EventID, type FunctionCall, data = the serialized input
2ReturnValuesBinaryConvertibleCollection<Package>: one nested FunctionReturn package per result
3Handle.FunctionCallIDUInt64. Counts up from zero and wraps below 262. Bit 63 set marks a call nobody answers (PublishEvent): the receiver delivers it and sends no FunctionReturn. An answer carries the call's handle, its answers and an empty Parameters package for the same ID (it used to echo the call's payload; readers use only the handle and the answers).
4Handle.ClientIDint32

NOTESEventDescriptor

All members are leaves or collections, so they appear in registration order: Expected (collection of strings), EventID (string), Returns (collection of strings; ["=Void"] for an event), RandomWeight (int32), Description (string), InputAnnotations and ReturnAnnotations (collections of NOTESFieldAnnotation, each six strings: Record, Field, Description, Min, Max, Default, empty when not given).

Typed (NOTES) event payloads

This layout and the signature that defines it are called NON (NOTES Object Notation); NON dynamic objects read and write it from the signature alone. For events hooked and fired through TypeSafeEVentNode, the payload is written by NOTESFlexibleSerDes in the canonical layout, which follows the event's agreed signature (grammar). It carries no names, tags or type IDs:

KindEncoding
Leaf (int32, string, NOTESVoid, custom leaves)The leaf's own ToBytes (see Primitive encodings).
RecordIts fields in ordinal order of their registration names, each in NOTES layout. No framing between fields.
Collectionint32 little-endian element count, then each element in NOTES layout. No per-element length prefix. Each element is at least one byte.
Optional fieldOne byte, 0 (absent) or 1 (present), then the value if present.

A Kennel with Street = "Main" and one cat Tom/7/3/Ann (signature [=Kennel, Cat{Age:UInt64,ID:UInt64,Name:string,Owner:string}, Kennel{Cats:Cat[],Street:string}]) is 44 bytes:

01 00 00 00                        Cats: count = 1
  03 00 00 00 00 00 00 00            Cat.Age   = 3      (UInt64)
  07 00 00 00 00 00 00 00            Cat.ID    = 7      (UInt64)
  03 00 00 00 54 6F 6D               Cat.Name  = "Tom"  (string)
  03 00 00 00 41 6E 6E               Cat.Owner = "Ann"  (string)
04 00 00 00 4D 61 69 6E            Street = "Main"      (string)

If the event's type is itself a leaf, the signature is just ["=float"] (for example), and the payload is exactly that leaf's own encoding (4 bytes for a float, 1 byte for NOTESVoid). A collection-typed event (["=string[]"]) is a count plus the elements.

That payload is the input of a FunctionCall (inside EVentFunction.Parameters). Each subscriber's acknowledgement is a NOTESVoid byte in ReturnValues.

Implementing this elsewhere

A non-.NET implementation must sort field names and signature entries the same way: ordinally, by UTF-16 code unit. Keeping names ASCII makes that a plain byte-wise comparison (memcmp). It also has to reproduce the signature strings exactly, including the [] / [<=N] suffixes. A cap tells a device without a heap how much to preallocate.

Note

Every parser validates lengths (negative, past the end of the buffer, counts above what the remaining bytes can hold) and rejects unknown package types; a frame must be consumed exactly. A frame or payload that doesn't parse drops the link with a LinkFault notice (Faults and re-joining), so a peer implementation must still produce exact frames, but a mistake no longer takes the other side's process down.
