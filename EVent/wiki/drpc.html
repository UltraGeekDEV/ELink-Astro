Distributed RPC (dRPC)

Scatter a call to every provider in the network, then gather all the answers.

The project describes dRPC as a call that “queries the entire sub network and queries a response from all interested parties as opposed to directly calling a single target.” In code, it's a scatter/gather over the same interest tables that events use.

Using it

dRPC basics
using EVent.CoreFunctionality;                          // EVentNode
using Event.CoreFunctionality;                          // LocalCallbackClient
using EVent.Connections.Models.BaseBinaryConvertibles;  // primitives

var node  = new EVentNode("Worker", new TCPServer(IPAddress.Any, 6001, "Worker"));
node.Run();
var local = node.AddLocalCallbackLayer();

// Provide: every node that registers "GetCoreCount" will answer.
local.RegisterFunction<BinaryConvertibleString, BinaryConvertibleInt32>(
    "GetCoreCount",
    request => Environment.ProcessorCount);      // int -> BinaryConvertibleInt32 (implicit)

// Call: blocks until every provider in the network has answered (or its link dropped).
List<BinaryConvertibleInt32> answers =
    node.CallFunction<BinaryConvertibleInt32, BinaryConvertibleString>("GetCoreCount", "all");

Console.WriteLine($"{answers.Count} providers, {answers.Sum(a => a.Value)} cores total");
Caution

The generic parameters are in opposite orders: RegisterFunction<TInput, TResult> but CallFunction<TResult, TInput> (I-34).

Notes:

  • If this node's local layer registered the function, it answers its own call. CallFunction doesn't exclude the local client.
  • If nobody provides the function, the call completes immediately with an empty list.
  • A provider that returns null, or whose result serializes to zero bytes, counts as not answering. Its entry is filtered out LocalCallbackClient.cs:93. That's why NOTESVoid serializes to one byte.
  • Several functions may be registered under one ID in one local client. Each contributes a result.
  • LocalCallbackClient.UnregisterFunction(id, handler) removes a provider; the node stops routing calls to the layer once it has neither functions nor event callbacks for the ID.

How a call travels

Downstream: HandleFunctionCall

  1. Deserialize the incoming EVentFunction (its handle is the caller's) EVentNode.cs:545–552.
  2. Create a new EVentFunctionHandle(client.ID). FunctionCallID comes from a process-wide counter, so the handle is unique in this process.
  3. Take a snapshot of events[EventID] without the sender. This is the awaiting set.
  4. Register a completion callback that copies the caller's handle back and sends a FunctionReturn to the sender.
  5. Send a FunctionCall with the new handle to everyone in the awaiting set.
  6. Call CheckFunctionCompletion. If the awaiting set is empty (a leaf), the call answers straight away with no results.

Upstream: HandleFunctionReturn and completion

HandleFunctionReturn EVentNode.cs:683–696 removes the responding client from the awaiting set and unions its ReturnValues into the pending call. When the set is empty, CheckFunctionCompletion EVentNode.cs:719–744 removes all bookkeeping, runs the optional OnFunctionCall hook (which can replace the aggregated EVentFunction), and invokes the completion callback.

What a provider does

When a FunctionCall reaches a LocalCallbackClient LocalCallbackClient.cs:64–131, it starts a thread-pool task and returns at once, so the delivering thread (a link's reader, or the local caller) is never held. The task runs every NativeFunction registered for the ID (concurrently; an async handler holds no thread while it awaits), wraps each non-empty result in a Package(EventID, FunctionReturn), appends it to ReturnValues, and writes a FunctionReturn back to the node through its channel.

Failure behaviour

SituationWhat happens
A responder's link dropsRemoveClient → HandleFucntionDrop removes it from every awaiting set, so the call completes with the results collected so far. That includes a link dropped for a fault (harness C08, C31).
A responder never answers (link stays up)After timeout (default FunctionCallTimeout, 30 s) the call completes with the answers collected so far, and every node on the path forgets it; a late answer is ignored (harness C36, C37). Answers held by a node in between that is itself still waiting are lost with it, because the caller's deadline doesn't travel with the call. A CancellationToken abandons the call early (C38).
A plain HookEvent subscriber exists for the same IDIts local layer answers with nothing, so the call completes without it (harness C05, N18; before commit 8c7a5cf the call hung).
A result fails to deserialize at the callerIt is silently dropped from the list (I-37).
A handler calls CallFunction itselfWorks, even back over the link its call came from: the handler doesn't run on that link's reader (harness C06, C32). Use RegisterAsyncFunction and CallFunctionAsync so the handler holds no thread while it waits. (Before commit 2c9a853 this deadlocked.)
A handler throwsThe node contributes no answer; the call completes and the link stays up (harness C33). (It used to drop the link the call came from.)

Custom serializer overloads

Both ends have overloads that bypass IBinaryConvertible.ToBytes/FromBytes:

// provider side
void RegisterFunction<TInput, TResult>(string EventID, Func<TInput, TResult> func,
                                       Func<byte[], TInput, bool> inputDeserializer,
                                       Func<TResult, byte[]> outputSerializer);
// caller side
List<TResult> CallFunction<TResult, TInput>(string EventID, TInput parameters,
                                            Func<TInput, byte[]> customInputSerializer,
                                            Func<TResult, byte[], bool> customResultDeserializer);

NOTES uses them to plug in its reordering NOTESFlexibleSerDes (see How EVent and NOTES fit). The deserializer delegates receive a pre-constructed instance to fill, and return false to reject the input.

Calls nobody answers

An event is a call whose answers are acknowledgements: every FireEvent carries the call object, handle, deadline timer and an answer round trip, which is what lets the publisher know every subscriber handled it. For a stream (sensor readings, telemetry) that is most of the cost, so a call can also be sent unanswered: PublishEventAsync on the typed node, publish on the C++ and JS leaves. The call's handle has bit 63 of its call ID set; a node that understands that delivers the call, sends no FunctionReturn and keeps no state for it, and a relay forwards the very frame it received. A node that does not understand it answers like for any call and the caller drops the answer, so the two kinds mix freely on one network. Order is kept per publisher and subscriber (an event ID's unanswered calls run one at a time, in order), and a publisher faster than a link is slowed by back-pressure, as for raw events. What is given up: the publisher can't know the event was handled. Measured numbers are in EVent/CoreFunctionality/THROUGHPUT.md.

The OnFunctionCall hook

EVentNode.OnFunctionCall(Func<EVentFunction, EVentFunction>) runs whenever any call completes on this node, whether local or in transit, and including NOTES' internal calls. If it returns a non-null value, that replaces the aggregated result sent upstream. You could use it to filter, audit or post-process answers, but its intended purpose isn't documented in the code (I-37).
